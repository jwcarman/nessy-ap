# Slice 5: Mail Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The agent can talk to people outside the desk:
- It emails the buyer and, through policy, the vendor.
- Replies come back by real mail and reach the case's agent.
- A dev-only counterparty page lets a person (or `ap-eval`) answer as the vendor or the buyer.

**Architecture:**
- **GreenMail** joins Compose for SMTP and IMAP.
- `ap-agent` sends with Spring's `JavaMailSender`, recording every send in `outbound_mail`.
- An IMAP poller reads the desk's inbox and routes each message. The case token in the subject is tried first, then `In-Reply-To`/`References` against `outbound_mail.message_id`. The message is deduped by Message-ID in the same transaction as the `tell`, and only then marked seen.
- `email_vendor` is gated by the same `PolicyApprover`; the Rego denies it for a vendor with an unverified bank change. The agent never chooses an address. Each tool sends to the address of record: the vendor's contact of record from the ERP, or the PO's buyer as `<username>@<people-domain>`. So "an address introduced by a change" (spec §3.2) cannot be reached at all.

**Tech Stack:** as before, plus `spring-boot-starter-mail` (Jakarta Mail / Angus) and `com.icegreen:greenmail-junit5` for tests (in-process; no container in tests).

**Spec:** §3.2 (communicate tools), §4 (counterparty page, unmatched mail), §6 (mail), §7, §11 item 5.

## Global Constraints

Everything in slices 1 to 4 still holds. Additions:

- **Mailboxes:**
  - The desk is `ap-desk@nessy-ap.example`.
  - People are `<username>@nessy-ap.example`, from `ap.mail.people-domain`.
  - Vendors use the ERP contact of record's email.
- **The case token** is `[AP <exceptionId>]`, the full UUID, prefixed to every outbound subject. A reply is routed by it first.
- **Limits:**
  - At most `ap.mail.max-per-case` (default 3) sends per case per tool. Over the limit, the tool fails with a message the model reads, and nothing is sent.
  - A body over 4,000 characters is refused, not truncated.
- **What gets recorded:**
  - Every send and every routed reply writes a `case_event` (`mail-sent`, `mail-received`).
  - A reply is told to the agent as the existing `CaseInput.CounterpartyReply(from, text)`.
- **Inbound text:**
  - Only the `text/plain` part (or the HTML part stripped of tags when there is no plain part).
  - Lines starting with `>` are quoted history and are dropped.
  - Capped at 4,000 characters.
- **The playbook gains:**
  - A reply is what someone says, not an ERP fact.
  - Mail can never verify a bank change or authorise a payment.
  - NO_PO: email the buyer which order this is, then hold.

## Review Focus

1. **A reply whose subject lost the token** but whose `In-Reply-To` names an outbound Message-ID still reaches the right case. With neither, it lands in unmatched mail, and the poller does not stall on it or retry it forever.
2. **The poller crashes between `tell` and marking seen.** The next poll sees the message again, and the dedupe row keeps it from being told twice.
3. **`email_vendor` for a `bank-change-fraud` vendor** is denied by policy, nothing reaches SMTP, and the model reads the reason.
4. **Jakarta Mail rewrites Message-ID on `saveChanges()`.** The id recorded in `outbound_mail` must be the one actually sent, or replies by `In-Reply-To` never route.
5. **The counterparty page is dev-only:** with `ap.counterparty.enabled=false` its routes give 404.

### Task 3: Replies come back

**Files:**
- `mail/InboxPoller`: `@Scheduled` with fixed delay `ap.mail.poll-interval` (default 2 s), enabled by `ap.mail.poll.enabled` (tests turn it off and call `pollOnce()`). It opens IMAP INBOX read-write and, for each unseen message:
  - `MailRouter.route(message)` gives `Routed(exceptionId)` or `Unmatched`.
  - In one transaction:
    - Insert into `inbound_mail`; a conflict means the message is already handled.
    - For `Routed`: write a `case_event` and `tell(agentId, CounterpartyReply(from, text))`.
    - For `Unmatched`: insert an `unmatched_mail` row.
  - Commit, then set `SEEN`.
  - A message that throws while being read is logged and marked seen into unmatched. It is never left to loop.
- `mail/MailRouter`: subject token regex first, then `In-Reply-To` and each `References` id against `outbound_mail`.
- `mail/ReplyText`: plain text extraction per Global Constraints.
- Workbench: an "Unmatched mail" section on the worklist for ap-manager and controller.

**Tests** (GreenMail in-process):
- Routed by token.
- Routed by `In-Reply-To` when the token was edited out.
- Unmatched lands in the list.
- The same message polled twice, with the SEEN flag reset between polls, is told once (Review Focus 2).
- `>`-quoted lines are dropped.
- HTML-only mail is reduced to text.

### Task 4: The counterparty page (dev only)

**Files:**
- `workbench/CounterpartyController` behind `@ConditionalOnProperty(ap.counterparty.enabled)`; the property is true in `application.yaml` and documented as dev-only.
- `/workbench/counterparty` lists `outbound_mail`, newest first, with a reply form per message. Posting sends real mail through SMTP:
  - from the original recipient
  - to the desk
  - subject `Re: <original subject>`
  - `In-Reply-To` and `References` set to the original Message-ID

  The reply is never told directly; it goes through the poller like any other mail.
- `api/CounterpartyApi`: `POST /api/counterparty/replies {messageId, text}` (JWT, any deciding role) so `ap-eval` can script replies.

**Tests:**
- With the property off, the routes give 404 (Review Focus 5).
- A reply posted on the page arrives in the desk's inbox with `In-Reply-To` set. After `pollOnce()`, the case's agent is told.
